# 系统架构与业务模型

## 技术架构

```text
浏览器（React 19 + Hash 业务路由 + 左侧导航）
  -> Vinext / Next App Router API
      -> 会话、RBAC、输入清洗、工资重算、状态机、审计
          -> Cloudflare D1（账号、资料、工资、部门、附件元数据、审计）
          -> Cloudflare R2（私有图片/PDF 字节）
```

客户端不是权威数据源。账号角色、工资金额、状态、部门名称、币种和附件所有权都在服务端重新检查。

## D1 表

- `payroll_users`：账号、密码派生值、角色、状态、工作负责人权限、资料 JSON、登录锁定。
- `payroll_sessions`：会话令牌摘要和过期时间。
- `payroll_salary_records`：所有者、状态、工作日期、金额、币种和完整业务快照。
- `payroll_salary_batches`：代报批次、幂等请求标识、请求摘要和目标员工。
- `payroll_recurring_rules`：按月固定排班模板、有效月份、启停状态、创建人和版本。
- `payroll_recurring_instances`：规则在各月份的唯一生成实例，防止手动或定时任务重复生成。
- `payroll_departments`：动态部门选项、排序和软停用时间。
- `payroll_files`：R2 key、所有者、原文件名、MIME 和大小。
- `payroll_file_references`：身份证件、收款资料、工资申报与文件的规范化引用。
- `payroll_settings`：注册开关和运行时标记。
- `payroll_audit_logs`：操作人、动作、目标、安全详情与时间。

## 不变量

- 空数据库首个账号固定为 `TabitoAdimin01@tabitoedu.com`，只有提交与服务端 `BOOTSTRAP_SECRET`（至少 16 个字符）一致的初始化密钥才能创建；账号密码另由部署者自行设置。
- 工作负责人必须是仍处于启用状态且已被管理员授予该权限的账号；工资记录保存负责人 ID 与姓名快照。
- 休息时间由申报人选择小时和分钟，不能超过本次工作的起止时长；时薪以整数分钟计算，不存在自动休息扣除或小数小时舍入误差。
- 币种只允许 `JPY`/`CNY`，任何统计不跨币种相加。
- 部门软停用不改写工资记录内的 `departmentLabel` 快照。
- 草稿才能修改/删除，待审才能通过/驳回，一条待审记录只能成功处理一次。
- 管理员和审核员按当前业务规则可以审批本人申报或自己代报的待审记录；审计仍完整保存工资所属人、创建人、提交人和审批人。
- 提交工资时必须指定工作月份，服务端只提交该月份的草稿，不影响其他月份。
- 同月多条草稿通过一个带版本条件的 D1 批处理提交，任一记录已被其他页面改动时整次提交失败；一次批量代报最多 62 条，同样全部成功或全部失败。
- 批量代报以 `requestId` 和请求摘要实现幂等重放；相同标识不得由其他操作人复用，也不能对应不同内容。
- 定期规则的编辑/删除使用乐观锁，同一规则同一月份只有一个生成实例。定时任务按小批次分页运行，以符合 D1 单次请求的查询和绑定数量限制。
- 已通过和已驳回记录继续归属它的 `workDate` 月份。
- 总审计选择员工账号后，月度、年度、逐月和部门汇总都只使用该员工的记录。

## 数据库升级

`drizzle/0000`–`drizzle/0006` 是生产数据库的唯一结构升级入口。部署前显式执行迁移；运行时只做只读兼容性探测，不在用户请求中建表、加列或回填数据。这样可以避免高并发请求重复执行 DDL，也便于备份和回滚评估。
